# Events

Status: DRAFT for approval. New 2026-10-15 (ADR-017, ADR-019). Events announce facts that have already happened. They travel through RabbitMQ from a transactional outbox to idempotent consumers. Commands (the saga steps) are not events; they are the HTTP calls in `INTERNAL_API.md`, driven from the durable `saga_commands` queue. Zod schemas for the envelope and every payload are in `packages/shared`.

## Envelope (all events)

```json
{
  "event_id": "01JABCDEF...",
  "type": "transfer.status_changed",
  "version": 1,
  "occurred_at": "2026-10-15T10:00:00.123Z",
  "producer": "transfers",
  "request_id": "01JREQ...",
  "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "subject": { "type": "transfer", "id": "uuid" },
  "payload": {}
}
```

`event_id` is a UUIDv7 generated by the producer inside the business transaction; it is the deduplication key. `occurred_at` is when the fact happened, not when it was published. It is UTC with exactly three fractional digits (`YYYY-MM-DDTHH:mm:ss.sssZ`), and `traceparent` has the W3C form `00-<32 hex>-<16 hex>-<2 hex>`; the shared schemas reject anything else.

## Broker topology

| Item | Definition |
|---|---|
| Exchange | `sahayak.events`, topic, durable |
| Routing key | `<type>.<qualifier>`, lowercase, bounded set of qualifiers (listed below) |
| Queues | One durable queue per consumer, bound by pattern; messages persistent; publisher confirms on; manual acknowledgement; prefetch 10 |
| Retry | A failed message goes to `<queue>.retry` (TTL 5 s, 30 s, 2 min, 10 min for attempts 1 to 4) and returns to the main queue; attempt count in header `x-attempt` |
| Dead letter | After 5 attempts the message goes to `<queue>.dlq`; any message in a DLQ raises an alert and is visible in the RabbitMQ management UI and the platform dashboard |
| Definitions | Exchanges, queues, bindings and DLQs are declared in `infra/rabbitmq/definitions.json` and also asserted by each consumer on start |

## Catalog

| Type (version) | Producer | Routing key | Consumers | Payload |
|---|---|---|---|---|
| `audit.recorded` (1) | `edge`, `assistant`, `wallet`, `transfers` | `audit.recorded.<producer>` | `audit` (queue `audit.ingest`) | `occurred_at`, `actor_id` or null, `actor_role` or null, `action`, `resource_type`, `resource_id`, `result` (`success`, `denied`, `error`), `request_id`, `details` (masked object) |
| `transfer.status_changed` (1) | `transfers` | `transfer.status_changed.<to_status>` in lowercase | `assistant` (queue `assistant.transfer_notices`, bound to `completed`, `failed`, `needs_review`) | `transfer_id`, `reference`, `user_id`, `from_status` (null when the transfer is created), `to_status`, `amount_minor`, `failure_code` or null, `origin_conversation_id` or null |

Every transfer status change publishes one `transfer.status_changed` event (all statuses, so future consumers can subscribe by routing key); only three have a consumer today. `audit.recorded` is published for each row in the audit action table of F07 by the service that performed the action. The `audit` service itself writes its own entries (`admin.view_audit`, `audit.verify`) directly into the chain and publishes nothing.

## Consumer rules

1. **Deduplicate.** Insert `event_id` into the `inbox` table in the same transaction as the effect; a duplicate key means acknowledge and do nothing.
2. **Tolerate disorder.** No ordering is guaranteed. The `audit` consumer appends in arrival order and keeps `occurred_at`. The assistant notification consumer acts on terminal statuses only and writes at most one notice per transfer and status (unique on transfer id and status in `messages.meta`).
3. **Validate on receipt.** A payload that fails its schema is a poison message: it goes straight to the DLQ with the validation error, without retries.
4. **Never block on other services.** A consumer's effect is local to its own database.
5. **Be safe to replay.** Replaying an old message must not change anything that a later message already changed.

## Producer rules

1. Insert the outbox row in the same transaction as the business change. No publishing from inside a request handler.
2. The relay publishes with confirms and marks the row published only after the broker confirmed. If the process dies in between, the event is published again; consumers deduplicate.
3. Details and payloads are masked before they enter the outbox.
4. Add fields only as optional within a version. A breaking change publishes a new `version` next to the old one until all consumers move. A contract test compares the schemas with committed snapshots in `packages/shared/events/__snapshots__` and fails on a breaking change.

## Guarantees and limits

At-least-once delivery with deduplication gives exactly-once effect per consumer. There is no global order. Event lag (time from `occurred_at` to the consumer's effect) is measured (`event_outbox_lag_seconds`, `audit_lag_seconds`) and alerted at 60 seconds; the healthy target is a few seconds. If RabbitMQ is down, producers keep committing business changes and the outbox grows; when it returns, the relay drains it.
