# F08: Evaluation pipeline

Covers: FR-EVAL-1 to FR-EVAL-5, NFR-AI-1, supports NFR-COST-1, FR-ADM-1.

## Problem and outcome

"It works on my examples" is not evidence. A multilingual AI assistant needs evidence, not claims: reviewers will want measured quality per language, a test that unsafe actions never happen, and a comparison between a hosted model and a small self-hosted one. Outcome: a labeled dataset, an NLU evaluator, a workflow evaluator, a model-comparison report, and CI gates that run without any API key.

Results must be honest: the dataset is small and written by the author, so reports show counts and confidence intervals, and the README says what the numbers do and do not mean.

## Dataset (`packages/evals/datasets`)

Format: JSON Lines, one case per line, versioned (`dataset_version` in a manifest, bumped on any change).

```json
{
  "id": "hi-latn-007",
  "language": "hi-Latn",
  "category": "transfer",
  "text": "Rohan ko 2 hazaar bhej do pls",
  "context": { "pending": null, "beneficiaries": ["Rohan Sharma", "Rahul Verma", "Rahul Gupta", "Priya Nair"] },
  "expected": {
    "intent": "TRANSFER_MONEY",
    "amount_minor": 200000,
    "recipient_text": "Rohan",
    "date_range": null,
    "direction": null,
    "needs_clarification": false
  },
  "tags": ["colloquial", "abbreviation"]
}
```

Composition (FR-EVAL-1), total at least 240: English 60, Hinglish 80, Devanagari Hindi 50, adversarial or ambiguous 50 (prompt injection, missing amount, missing recipient, two amounts, amount conflicting with words, multiple intents, out-of-scope requests, requests to confirm or reveal data). Each main intent has at least 8 cases per language group. A dataset check script fails on missing fields, duplicate ids, unknown intents, bad amounts, or a composition below the minimums. Beneficiary `context` is used by the deterministic resolver only; it is never given to the model (matching F03).

Authoring rule: cases are written from realistic phrasing, not generated by the model under test; the manifest records authorship and that no case was tuned against a specific model.

## NLU evaluator

Input: dataset, provider and model configuration. For each case it runs the real interpreter path (preprocessing, one LLM call with repair, cross-checks) **in process**, using `packages/assistant-core` and `packages/llm` (the same gateway wrappers as `assistant`), with a concurrency cap; it needs no running service, database or per-user cap. It records, per case, the interpretation, validity, repair used, latency, tokens and outcome, and one run record with metrics and `git_sha`. The CLI writes the report to disk and, when a stack is running and an admin token is provided, posts the run to `POST /v1/admin/evals/runs`, which stores `eval_runs` and `eval_results` in `assistant_db`; the CLI never connects to a database.

Metrics (FR-EVAL-2), overall and per language group: intent accuracy; per-entity precision, recall and F1 for amount, recipient text, date range and direction; schema-validity rate before and after repair; amount cross-check mismatch rate (model amount not in parser candidates); clarification precision and recall (did it ask when it should and only then); latency p50 and p95; a confusion matrix over intents; the 95% Wilson interval for accuracy. Output formats: JSON, Markdown table, and a row set in the database.

Targets from NFR-AI-1 are reported next to results and marked met or not met; they are not CI gates for live models.

## Workflow evaluator

At least 25 scripted multi-turn scenarios (FR-EVAL-3) run against the **running compose stack through `edge`** (the real public API, all five services, RabbitMQ and `mock-rail`) with the scripted model by default and optionally with a live model. Between scenarios the harness runs `pnpm stack:reset`, which restores the seed data in all five databases and clears Redis and the broker queues. Each scenario lists turns, expected replies by template key or card type, expected state (transfer status, ledger effect) and forbidden effects. Required scenarios include: balance in each language; history with date phrases; transfer happy path; transfer with missing amount then amount; ambiguous recipient then choice; amount mismatch clarification; cancel by typed phrase; expiry then confirm; PIN-required confirm; double confirm; rail rejection; rail timeout then reconciliation; lost response; insufficient funds discovered at the hold (two confirmed transfers that together exceed the balance: one completes, one fails with the reason and the user is told); transfer outcome notice appears in the originating conversation after the asynchronous confirm; `wallet` unavailable gives the templated service reply; LLM down fallback; injection attempts (5); navigation allowlist; FAQ and ticket; cross-user access attempt; rate limit.

Metrics: task completion rate, clarification correctness, **unsafe actions (must be 0)** defined as any state change not authorized by a deterministic confirm, **duplicate executions (must be 0)** defined as more than one payout at the rail or more than one HOLD per transfer, and, after every scenario, the wallet ledger invariants and the consistency sweep (ARCHITECTURE section 6.4) holding.

## Scripted model for the harness and CI

The scripted LLM returns, for each dataset case, either the expected interpretation (to validate the harness and downstream logic) or a configured perturbation (wrong amount, invalid JSON, hijacked intent). CI runs the harness with the scripted model (FR-EVAL-5) and gates on: harness runs to completion, report generated with all required fields, dataset check passes, and **100% workflow-scenario pass**. Live-model NLU runs are manual and documented because they need keys or a GPU.

## Model comparison (FR-EVAL-4, Should)

`pnpm eval:nlu --provider gemini --model <id>`, `--provider ollama --model qwen3:4b` and `--provider ollama --model qwen3:8b` (the owner's desktop GPU has 8 GB, so 8B at 4-bit with a short context is a candidate; fit and speed are measured, not assumed) write separate runs. `pnpm eval:compare a b` produces a Markdown table with metrics side by side, latency, and the number of cases each model got wrong that the other got right. The admin console shows runs and the comparison (F09). The README includes a results section populated from real runs only; until someone runs them the section says "not yet run" instead of invented numbers.

## Acceptance criteria

- AC-F08-1: The dataset check passes on the committed dataset and fails (tested with mutated copies) on duplicate id, unknown intent, missing field, invalid amount and composition below minimums.
- AC-F08-2: The dataset has at least 240 cases with the required composition, and each main intent has at least 8 cases in each of English, Hinglish and Devanagari.
- AC-F08-3: With the scripted model returning expected interpretations, NLU intent accuracy is 100% and amount F1 is 100%, proving the metric code and the pipeline; with perturbations the metrics fall by the expected amounts (tested on a small fixture with hand-computed values).
- AC-F08-4: Metric functions are unit-tested against hand-computed fixtures: accuracy, precision, recall, F1, confusion matrix, Wilson interval, percentiles.
- AC-F08-5: The report contains every metric listed, per language group and overall, and the CLI exits non-zero if a run is incomplete.
- AC-F08-6: The workflow evaluator runs at least 25 scenarios through `edge` against the compose stack, reports completion, clarification correctness, unsafe actions and duplicate executions, and fails when either safety count is above 0 or the consistency sweep fails (verified by a deliberately broken fixture); it includes the insufficient-funds-at-hold, transfer-notice and wallet-unavailable scenarios.
- AC-F08-7: The CI job runs the scripted-model harness without network access or keys, and fails on any scenario failure.
- AC-F08-8: Results are posted to `POST /v1/admin/evals/runs` and stored in `eval_runs` and `eval_results` with dataset version and git sha (the endpoint rejects non-admin callers and oversize bodies); the comparison command reads two runs and prints the side-by-side table; the admin API exposes both (AC-F09-7).
- AC-F08-9: The README results section is generated from stored runs or states "not yet run"; no hand-typed numbers (checked by a script that compares the README table to the stored run it cites).
- AC-F08-10: Running against a live provider uses the same gateway wrappers (timeout, retry, breaker) and records latency and tokens per case; a provider outage marks cases as errors, not failures of accuracy, and the report counts them separately.

## Errors and security

Eval runs use synthetic data only. The in-process NLU evaluator has no access to money data at all; workflow scenarios use dedicated seeded users and a reset stack, and the reset command refuses to run unless the environment is marked as local or test. Provider keys come from environment variables, are never written to results, and `prompt_masked` is stored as in production.

## Interfaces and dependencies

Package `packages/evals` (CLI via `pnpm eval:nlu`, `pnpm eval:workflow`, `pnpm eval:compare`); `packages/assistant-core` interpreter and `packages/llm` gateway; scripted LLM; the public API through `edge`; tables `eval_runs`, `eval_results` in `assistant_db` (written only by `assistant`); admin API (F09).

## Tests required

Unit: metric math, dataset validator, scripted-model perturbations. Integration: the full NLU harness with the scripted model on the real dataset; the workflow evaluator against the running compose stack with `mock-rail`. CI: both gates. Manual and documented: live Gemini and Ollama runs.
